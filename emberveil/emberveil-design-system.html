Canonical family reference

Warm semantic light. Disciplined structural calm.

Emberveil is a paired interface and syntax system for prolonged work. Dark mode feels like colored light inside a muted Mirage atmosphere. Light mode feels like semantic ink printed on dim paper. The roles remain stable; the material expression changes.

Use this document as the source of intent when designing a new application, translating Emberveil to another platform, or reviewing whether an implementation still belongs to the family.

Design principles

These rules define Emberveil more reliably than any individual hex value. Preserve them when a platform forces color substitutions or component-specific compromises.

Comfort first

Avoid pure black and broad white. Long sessions should feel steady, not brilliant.

Warm execution

Orange and amber identify decisions, control flow, actions, and callable behavior.

Cool structure

Cyan and teal describe types, navigation, information, and architectural boundaries.

Localized color

Large surfaces stay quiet. Saturation belongs to small semantic marks, never decorative acreage.

AtmosphereWarm-neutral, slightly smoky, and modern. Never pitch black, sterile white, cobalt-dominant, or nostalgically sepia.
HierarchyCreate depth with close material steps. Borders are quiet; focus indicators and readable content carry the stronger contrast.
SemanticsA role keeps its meaning across modes. Orange does not become informational blue merely because the background changed.
RestraintPlain variables, object keys, data fields, and CSS properties remain neutral so code stays calm and keywords retain authority.

One family, two materials

The modes are siblings rather than inversions. They share semantic grammar but tune luminance, saturation, borders, elevation, and text independently.

Emberveil Dark

Light inside atmosphere

Warm charcoal, smoky slate, softened cyan, lichen green, and localized amber illumination. Built around Ayu Mirage as the dominant contemporary influence.

Pressed fiber, parchment, charcoal ink, burnt orange, deep teal, olive, and ochre. Bright enough to be light, never bright enough to glare.

Neutral is an active choice

Variables, object keys, JSON/YAML keys, fields, member properties, and CSS property names use the main foreground. This lowers visual noise and protects orange for genuine language structure.

Coral has a narrow job

Reserve coral/rust for markup attributes, events, and selected domain-specific member semantics. Do not treat every key-value pair as an attribute.

Syntax language

Code coloring follows meaning and reading rhythm. Warm tones describe execution, cool tones describe structure, green contains content, mauve marks constants and annotations, and neutral text carries ordinary data.

Typography

Typography should support the color system rather than compete with it. Emberveil favors familiar, highly legible system faces and restrained weight changes.

Build calm systems.
Warm structure without visual noise

Use the platform UI sans-serif for product interfaces. Prefer a proven monospaced family for code, logs, identifiers, and tabular technical data. Keep body copy between 14–17px and never use thin weights on muted text.

const theme: Emberveil = resolve(mode);

UI text

System sans-serif, weight 400. Use 500 only for headings, buttons, selected navigation, and compact labels.

Code text

Platform monospace with clear punctuation and distinguishable glyphs. Let syntax color carry most hierarchy.

Line height

Use 1.45–1.7 for prose and 1.55–1.8 for code. Dense data tables may tighten carefully.

Layout and material depth

Emberveil does not rely on dramatic cards or floating glass. Most structure comes from spacing, close surface steps, thin borders, and a small number of genuinely raised elements.

Spacing

Use a 4px base rhythm. Prefer 8, 12, 16, 24, 32, and 48px. Increase whitespace before adding borders.

Radii

5px for controls, 9px for panels, 14px for major dialogs or composed app frames. Avoid bubbly geometry.

Elevation

Attached panels use borders and material shifts. Reserve shadows for dialogs, menus, and major floating surfaces.

Do

  • Let adjacent surfaces differ subtly.
  • Use one thin focus edge.
  • Keep status bars neutral.
  • Use raised paper or slate only where elevation is real.

Do not

  • Use pure black or broad pure white.
  • Turn sidebars into saturated blue blocks.
  • Outline every region strongly.
  • Use orange as a large decorative background.

States and feedback

Status colors communicate outcomes, not decoration. Pair them with language, icons, or shape so meaning never depends on hue alone.

InfoTeal explains structure, navigation, or a neutral process state.
SuccessGreen confirms completion, health, or a positive result.
WarningAmber marks a condition requiring attention without implying failure.
ErrorRed is reserved for destructive action, invalid input, and failed outcomes.

Focus and selection

Focus is a narrow gold or ochre ring. Selection is a cool subdued wash. Never substitute the orange action color for keyboard focus.

Hover and active

Hover shifts one material step. Active navigation adds a narrow orange marker and stronger text; it does not require a saturated fill.

Disabled

Reduce contrast and remove interactive emphasis while preserving labels. Do not make disabled controls disappear completely.

Loading

Use neutral structure with one moving focus-colored indicator. Avoid animating large orange or cyan regions.

Accessibility and comfort

Emberveil’s low-glare character must not become an excuse for unreadable content. Comfortable surfaces and strong text can coexist.

Contrast targets

  • Body text: target at least 4.5:1.
  • Large text and essential icons: at least 3:1.
  • Focus indicators: visibly distinct from adjacent surfaces.
  • Muted metadata may be quieter, but never carry essential instructions alone.

Color independence

  • Add text to every status.
  • Use icons or shapes for chart categories when needed.
  • Underline links in prose-heavy contexts.
  • Do not distinguish errors from success using color alone.

Motion

  • Keep transitions brief and functional.
  • Honor reduced-motion preferences.
  • Never pulse large colored surfaces continuously.
  • Preserve state changes when animation is disabled.

Light environments

  • Test Emberveil in bright offices and dim rooms.
  • Do not brighten the canvas toward white to solve every contrast issue.
  • Raise foreground or local boundary contrast first.
  • Test actual devices, not screenshots alone.
Known edge caseThe current light terminal maps explicit ANSI white close to its paper background. Ordinary terminal foreground remains readable. Keep the mapping until real software demonstrates a practical failure, then test a semantic remap rather than changing it from theory alone.

Implementation blueprint

Build applications from semantic tokens. Components should never know that a keyword is orange or a canvas is charcoal; they should consume roles that can evolve across modes and platforms.

Recommended token layers

1. Core

Raw family colors. Do not use directly in product components.

2. Semantic

Canvas, text, action, focus, success, danger, syntax roles.

3. Component

Button, input, navigation, dialog, table, editor, terminal.

4. Platform

VS Code, web, desktop, terminal, documents, charts.

Build sequence

  1. Choose semantic tokens before drawing components.
  2. Implement both modes from the first component.
  3. Set the canvas, shell, sidebar, panel, and raised ladder.
  4. Establish primary, muted, and faint text roles.
  5. Add focus and selection before hover decoration.
  6. Build buttons, inputs, navigation, tables, and dialogs.
  7. Apply orange only to decisions and primary actions.
  8. Use teal for structure and information.
  9. Test empty, loading, error, success, and disabled states.
  10. Audit keyboard navigation and focus visibility.
  11. Test at 320px, tablet, desktop, and wide layouts.
  12. Review the result in bright and dim physical environments.

Governance and quality bar

A theme family stays coherent when changes are judged against intent, real use, and both modes—not only against isolated color samples.

Change ruleStart with a concrete failure screenshot or repeated daily-use problem. Avoid palette changes based only on theoretical discomfort.
Pair ruleEvaluate every semantic change in both modes. Equivalent meaning does not require numerically mirrored values.
Scope rulePrefer the narrowest correct token or syntax scope. Do not fix one language by recoloring an unrelated category globally.
Review ruleTest source code, prose, JSON, CSS, markup, Rust annotations, terminal output, completion lists, selection, diffs, and secondary metadata.
Release ruleDocument intent, validate tokens, visually inspect representative applications, and record deliberately deferred findings.

Definition of Emberveil-complete

An implementation belongs to the family when it is comfortable for prolonged use, recognizable in both modes, semantically consistent, fully keyboard-operable, readable without relying on maximum contrast, and calm enough that content—not the theme—remains the center of attention.

Emberveil — muted atmosphere, warm decisions, cool structure.
